工具與工作流 · 2026-09-30

跨專案 PR 開發與交付工作流

所有 Git 專案都採用同一套預設交付路徑：同步 Base → 建獨立 Branch → 實作 → 驗證 → Commit → Push Branch → PR → CI / Diff / 風險審查 → Squash Merge → Readback / Deploy。

目的不是讓 Git 變複雜。而是讓每一項變更都有清楚邊界、驗證證據、合併紀錄與回檔入口，尤其適合多功能或多 Agent 同時開發。

一個工作單元一個 Branch

類型命名用途
Featurefeat/*新功能
Fixfix/*Bug 修復
Docsdocs/*文件與 Wiki
Hotfixhotfix/*緊急修復，仍走 PR
Revertrevert/*撤銷已合併變更

PR 是正式整合入口

PR 至少記錄目的、變更範圍、驗證結果、風險、相依項、部署方式與回檔策略。Push Branch 不等於交付；CI 綠燈也不等於已 Merge 或 Production 已發布。

多功能／多 Agent 並行

  1. A、B、C 各自建立 Branch 與 PR。
  2. 若 B 依賴 A，在 PR 明確標記相依，不偷複製 A 的未合併程式。
  3. A Merge 後，B/C 更新最新 Base、解衝突、重跑必要驗證。
  4. 衝突在 Branch 解決，不用 force push 或 reset 整合分支。
  5. Agent 間用 Issue、PR 與 authoritative repo 文件交接，不讓人充當人工剪貼板。

回檔

一般程式與文件使用 revert/* Branch 對 Merge Commit 做 Revert，再開 Revert PR。資料庫與外部服務則需要額外的備份、向前修復或資料復原方案；Git Revert 不會自動復原 Production 資料。

固定交付紀錄

Repo | Base | Branch | PR URL/# | Head SHA
CI/Validation | Merge SHA / pending
Deploy/readback | Revert plan
