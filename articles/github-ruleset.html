GitHub Ruleset 與 PR 合併閘門

工作流程告訴人與 Agent「應該怎麼做」；Ruleset 則讓 GitHub 在伺服器端阻止直接繞過 PR、必要 CI、force push 或刪除受保護分支。

建立前先讀實際 Default Branch

不要因為慣例就假設一定是 main。先從 repository metadata 讀取實際 default / integration branch，再用 Include default branch 套用規則。

個人專案的基準設定

Ruleset建議
EnforcementActive
Bypass list保持空
Require pull request開啟；個人專案 approvals 可先設 0
Required status checks只加入實際存在且穩定的 CI job context
Require branches up to date並行開發時建議開啟
Block deletions / force pushes開啟
Signed commits / deployments / code scanning沒有對應能力前不要為了「看起來嚴格」亂開

實例：PersonalWorkStation

實際設定要求 PR 必須經過 verify 檢查並只允許 Squash Merge。驗證時曾在 CI 仍 pending 時嘗試合併，GitHub 明確拒絕；待檢查成功後才可 Merge。

證據邊界：「PR pending 時合併被拒」可以證明 PR/CI 閘門有效，但不能等同於「已實測直接 push 被拒」。每一種保護都要照實記錄證據範圍。

常見問題

Ruleset 名稱只是辨識用，不會決定 Target；真正重要的是 Enforcement、Target、Required checks 和 Bypass。選錯不存在的 status check 反而可能把 PR 永久鎖住。
